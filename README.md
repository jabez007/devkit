# Devkit

Composable developer checks, built from scratch. Install the foundation, select
plugins for a project, and authorize their commands through an operator policy.
The CLI, Python API, and optional local MCP server share validation, authorization,
and evidence handling.

The v0.6 milestone adds an optional [Beads integration](docs/Beads_Integration.md):
inspect work items and explicitly associate verification evidence without changing
task status. Go checks and offline Odoo 19 validation remain independently usable.
The foundation requires no Beads, Odoo server, Docker, or model credentials.
Package names and the plugin API remain provisional; nothing is published to a
public package registry. Versions are foundation 0.1.2, Beads/Go/MCP 0.1.0, and
Odoo 0.5.0. Plugin API 1.0 and evidence envelope 1.0 are unchanged.

## Set up a development checkout

The tested baseline is Linux, Python 3.12, uv 0.9.5, and Go 1.24.4. Go is needed
only for Go checks. Dependency versions are pinned in [uv.lock](uv.lock).

```sh
uv sync --all-packages --locked
source .venv/bin/activate
devkit --version
devkit --json doctor
devkit plugins
```

Installing a plugin makes it discoverable. It does not activate or authorize it.
`doctor` checks the activated registry and declared environment prerequisites;
with no plugins selected, it checks only the foundation. It does not validate a
project. Run a command or check profile after doctor succeeds. Activation errors
identify the affected plugin; configuration errors name the settings file.

To install built distributions in another environment:

```sh
uv build --all-packages
uv venv /tmp/devkit-install --python 3.12
uv pip install --python /tmp/devkit-install/bin/python dist/devkit-0.1.2-py3-none-any.whl
# Add only the plugins and adapters you need:
uv pip install --python /tmp/devkit-install/bin/python dist/devkit_go-0.1.0-py3-none-any.whl
uv pip install --python /tmp/devkit-install/bin/python dist/devkit_odoo-0.5.0-py3-none-any.whl
uv pip install --python /tmp/devkit-install/bin/python dist/devkit_mcp-0.1.0-py3-none-any.whl
uv pip install --python /tmp/devkit-install/bin/python dist/devkit_beads-0.1.0-py3-none-any.whl
```

Use the supplied foundation wheel, since the working distribution name is not an
owned public namespace. The installed-wheel acceptance script constrains registry
dependencies to the lockfile; ordinary wheel installs use the declared ranges.

## Configure a project

Put [examples/devkit.toml](examples/devkit.toml) in the project you want to check.
Keep only the installed plugins and relevant checks. For Odoo alone:

```toml
schema_version = 1
plugins = ["odoo"]
timeout = 90

[options.odoo]
target_version = "19.0"
addons_paths = ["addons"]
strict_dependencies = false

[profiles]
static = ["odoo.manifests"]
```

Settings come from `$XDG_CONFIG_HOME/devkit/settings.toml` (default
`~/.config/devkit/settings.toml`), then the selected project's `devkit.toml`.
Project values replace entire top-level tables; nested tables are not merged.
`--timeout` overrides the configured deadline. Relative addon paths resolve
against `--project`, independent of the caller's working directory. Unknown
settings keys and invalid types fail configuration validation.

## Authorize commands

Create or merge [examples/policy.toml](examples/policy.toml) into
`$XDG_CONFIG_HOME/devkit/policy.toml`, default `~/.config/devkit/policy.toml`.
The policy must be outside the selected project. Set its mode to `0600` and
replace the example project paths with the project's absolute path.

```toml
[trusted_plugins]
devkit-odoo = "0.5.0"

[commands."odoo.module.validate"]
project = "/absolute/path/to/project"
effects = ["read_fs"]
surfaces = ["cli", "python", "mcp"]
```

Trust is bound to the normalized distribution name and exact installed version.
For automated or third-party installations, optionally pin a reviewed wheel as
well. Keep the approved wheel available locally and obtain its SHA-256 from your
trusted build or download process:

```toml
[trusted_plugins.devkit-odoo]
version = "0.5.0"
wheel = "/absolute/operator/path/devkit_odoo-0.5.0-py3-none-any.whl"
sha256 = "<64 lowercase hexadecimal characters>"
```

This table replaces that distribution's version-only entry. Before importing any
selected plugin, devkit checks the wheel's actual digest and compares its payload
with installed files. A mismatch fails activation with `ARTIFACT_MISMATCH`.
Evidence records `producer.artifact_sha256`; version-only trust records null.
Changing the trusted version or digest revokes an existing service's approval
until it is recreated.

Verification currently supports ordinary wheels installed directly into
site-packages. Editable installs, `.pth` files, packaged bytecode, relocated
`.data` payloads, and symlinked installed payloads fail closed. Installer-generated
wrappers, rewritten `RECORD`, and generated bytecode caches are outside the
comparison. The check follows the [wheel installation format](https://packaging.python.org/en/latest/specifications/binary-distribution-format/).
It does not verify signatures, dependencies, import-path shadowing, cached code,
or modifications after activation. Continue to use trusted installation and
runtime isolation; this is a content check, not execution isolation.

Legacy command grants bind a command to one project, declared effects, and surfaces.
The top-level `deny = ["command.id"]` list overrides grants. Policy is checked
again on each invocation; changing repository settings cannot grant permission.
For several repositories, define reusable profiles in the operator policy:

```toml
[profiles.odoo_static]
projects = ["/absolute/path/to/repo-one", "/absolute/path/to/repo-two"]

[profiles.odoo_static.commands."odoo.module.validate"]
effects = ["read_fs"]
surfaces = ["cli", "python", "mcp"]
```

Each project must be an explicitly listed, canonical absolute path. There are no
wildcards or implicit descendant scopes. Adding a project to this external
operator file is the approval step; repository configuration cannot enroll itself.
A profile may contain `deny = ["command.id"]` beside `projects`. Any applicable
denial wins over other profiles and legacy grants. One complete grant must allow
the command's effects and requested surface; fragments from different profiles
are never combined. Plugin trust remains separate. Profiles in `devkit.toml`
still select checks and cannot define operator grants.

Go tests execute repository code and require all five effects: `read_fs`,
`write_fs`, `execute_process`, `network_read`, and `network_write`. Grant MCP
access separately by adding `mcp` to the command's surfaces when needed.
Policy declarations do not sandbox Python plugins or Go tests. Use host isolation
for untrusted code. Package installation itself also lies outside this policy.

## Run and inspect checks

Global flags precede the subcommand:

```sh
devkit --project /absolute/path/to/project plugins validate
devkit --project /absolute/path/to/project commands
devkit --project /absolute/path/to/project --json run odoo.module.validate
devkit --project /absolute/path/to/project --json run odoo.module.validate --args '{"module":"example"}'
devkit --project /absolute/path/to/project --json check static
devkit --project /absolute/path/to/go-project --timeout 120 --json run go.test
```

Go runs `go test -json -count=1 ./...` with the locally installed toolchain,
filtered environment, bounded output, and a shared deadline. Passing, failing,
and skipped tests are counted separately. No executed tests produces `blocked`,
including projects whose tests all skip. No toolchain is downloaded automatically.

Odoo validation parses bounded literal manifests without executing them. It
checks selected field types, the version format, module names, duplicate addons,
and declared data/demo paths. Paths must stay inside the project and module.
Dependencies are resolved, missing, unknown, or invalid. Inventories are
incomplete by default: absent `base` or `sale` in a custom-only repository is
unknown, not a module defect. An explicit `inventory.complete` or
`inventory.complete_prefixes` claim makes absence a confirmed failure for the
claimed scope. `strict_dependencies=true` blocks on unknown dependencies;
confirmed missing and invalid dependencies fail regardless of strict mode.
Success does not establish runtime, database, XML, asset, or external dependency
compatibility. Declared data/demo XML is parsed automatically. Malformed XML
fails with a file and location; unsupported features and inspection limits block
coverage. Literal XML references report earlier local definitions or explain why
resolution is unknown. Repeated IDs remain valid update candidates. Unknown XML
references are advisory, and `strict_dependencies` still concerns module names.
Declared CSV is also inspected for flat structure, UTF-8, IDs and direct relational
references. XML can use earlier CSV declarations and CSV can use earlier XML or
CSV declarations. Unsupported layouts block coverage; empty files and invalid
UTF-8 fail. Ordinary cell values are never executed or returned in evidence.
Dependency cycles among inspected manifests fail with a closed path to review.
Unknown dependencies and uninspected manifests remain explicit gaps; selecting
one module does not inspect its dependencies' manifests. No cycle observed is
not a claim that the runtime installation is cycle-free.
See [Odoo validation](docs/Odoo_Validation.md) for multiple addon
paths, scoped completeness, coverage, bounds, and result-schema compatibility. The profile follows [this pinned Odoo 19 source](https://github.com/odoo/odoo/blob/005e0a0eb7ef80cd15b0c82b570b2b0843181ba2/odoo/modules/module.py).

Profiles list check IDs: `go.tests` and `odoo.manifests`. Every required check
must succeed. Child runs have their own evidence and share the profile's deadline
and cancellation signal. An empty profile is blocked; unknown IDs are errors.
Profiles contain at most 128 unique check IDs. Plugin environment checks run
before that plugin's commands and during `doctor`, through the same policy path.

| Result | CLI exit | Meaning |
| --- | --- | --- |
| `success` | 0 | The declared operation completed successfully. |
| `failed` | 1 | An executed check found a problem. |
| `blocked` | 2 | Authorization, a prerequisite, tool, or required coverage is missing. |
| `error` | 3 | Configuration, input, output, execution, deadline, or evidence failed. |
| `cancelled` | 130 | Execution was cancelled. |

`--json` emits one JSON document. Command results contain a stable `reason` code,
domain data, and an `evidence_path`. Read the JSON or evidence for details when a
text summary is insufficient. `plugins` lists installed metadata without imports;
`commands` lists only commands authorized for the CLI. `plugins validate` checks
activation and runs `doctor`; behavioral contract tests run in the test suite.

## Evidence and execution limits

Each invocation writes `$XDG_STATE_HOME/devkit/runs/<uuid>/result.json`, default
`~/.local/state/devkit/runs/<uuid>/result.json`. Run directories use mode `0700`
and results `0600`; writes are atomic. The envelope records arguments, producer
version, timestamps, source revision and dirty state, result, and diagnostics.
Unavailable Git metadata is `null`. Project identity is the SHA-256 of its
resolved local path, so moving the project changes that identity.

Known secret environment values and credential patterns are redacted before
returning or persisting results. Redaction cannot recognize every secret; avoid
putting secrets into command arguments or output. Handler results and arguments
are limited to 1 MiB of JSON; subprocess streams to 256 KiB each; captured Python
diagnostics to 16,384 characters. Arbitrary artifact attachments are not implemented.
The response adds `evidence_path` after writing
the file. An evidence failure returns `EVIDENCE_WRITE_FAILED` and preserves the
actual outcome as `observed_result`, without rerunning the command.

Managed subprocesses are terminated as a Linux process group on timeout or
cancellation. A process that deliberately detaches can escape this mechanism.
Trusted Python handlers must cooperate with cancellation and deadlines; the
runtime cannot forcibly stop arbitrary in-process code. Invocations serialize
Python output capture, and the MCP server handles one tool invocation at a time.
Native file-descriptor writes by plugins are outside Python output capture.

## Use the existing checks in CI

The [CI pilot guide](docs/CI_Pilot.md) runs a combined Go/Odoo project from built
wheels, creates an external operator policy, preserves nonzero check results and
retrieves parent/child evidence. The acceptance matrix tests seven recipe scenarios,
including failed checks, blocked coverage, policy diagnostics and evidence-command
failures. No Odoo server or new adapter is required.

## Inspect and retain evidence

Evidence maintenance works without loading project settings or plugins. Global
flags still precede the subcommand:

```sh
devkit --project /absolute/path/to/project --json runs list --limit 50 --offset 0
devkit --project /absolute/path/to/project --json runs show <run-uuid>
devkit --project /absolute/path/to/project runs pin <run-uuid> --reference work:active-123
devkit --project /absolute/path/to/project runs prune
devkit --project /absolute/path/to/project runs prune --apply
devkit --project /absolute/path/to/project runs unpin <run-uuid> --reference work:active-123
```

The default scope is the selected project. Add `--all-projects` after the run
operation to inspect or maintain the entire local store. Listing supports a
limit of 1 to 1,000 and an offset. These operator commands do not create new
run evidence or expose MCP tools. Local filesystem access controls maintenance;
project command grants do not grant or restrict this operator interface.

`runs prune` previews eligible UUIDs and explains why other runs are protected.
Only `--apply` deletes evidence. Defaults retain runs from the last 30 days and
at least the latest 100 completed runs per project. Both conditions must permit
deletion. Configure `$XDG_CONFIG_HOME/devkit/retention.toml`, default
`~/.config/devkit/retention.toml`, outside the selected project and with mode `0600`:

```toml
max_age_days = 30
keep_last = 100
```

Operator flags `--older-than-days` and `--keep-last` override these settings.
Repository `devkit.toml` cannot configure retention. No background job is
installed; invoke the command from an operator-controlled schedule if needed.

Register a reference with `pin` before publishing a run link or associating it
with active work. Pins are idempotent, can hold several references, and have no
automatic expiry. `unpin` removes only the named reference. Any remaining
reference or embedded `work_item_ref` protects the run. Devkit cannot discover
links in external trackers yet, so unregistered external links are not protection.

Protection extends through parent/child check families. Families with missing
or unfinished members are retained, as are directories containing unmanaged
files. Corrupt evidence, invalid reference metadata, or unsafe symlinks block
pruning before any deletion. Writers, reference updates, and pruners share a
Linux filesystem lock; apply recomputes eligibility while holding that lock.
Cooperating concurrent pruners cannot delete the same run twice. If deletion
fails, pruning stops and reports completed deletions and the error. An operating
system interruption can leave partial removal; family deletion is not a filesystem
transaction. The next attempt preserves unreadable or incomplete evidence.

## Python and MCP

```python
from pathlib import Path
from devkit.app import create_service

result = create_service(Path("/absolute/path/to/project")).execute(
    "odoo.module.validate", {"module": "example"}
)
```

For an MCP client's local stdio server configuration, use the absolute path to
`devkit-mcp` in the environment containing the adapter:

```json
{
  "command": "/absolute/path/to/environment/bin/devkit-mcp",
  "args": ["--project", "/absolute/path/to/project"]
}
```

The adapter generates tools from authorized commands and rechecks policy on
calls. It returns the same envelope in structured content. The tested SDK is
MCP 1.30.0 with protocol 2025-11-25. Remote hosting is outside this release.

## Develop a plugin and verify changes

Start from [examples/plugin](examples/plugin), a separate wheel with one command
and one check. See [the plugin guide](docs/Plugin_Contract.md) for the contract,
registration rules, tests, and cancellation requirements.

```sh
uv run ruff check .
uv run ruff format --check .
uv run mypy
uv run lint-imports
uv run pytest
DEVKIT_BEADS_BINARY=/absolute/path/to/bd-1.3.2/bd uv run python scripts/check_wheels.py
```

[CI](.github/workflows/checks.yml) runs these checks on Ubuntu 24.04 using Node 24
action releases. Ruff includes a maximum cyclomatic complexity of 10;
strict typing covers the runtime packages. The wheel matrix builds packages and
tests the original seven environments (foundation, Go, offline Odoo, template,
artifact trust, MCP composition, and CI pilot), plus a renamed third-party plugin,
real Beads with Go and Odoo, and two foundation-only portable-evidence readers.
The Beads matrix needs the explicitly selected 1.3.2 test binary; see the
[download/checksum and compatibility instructions](docs/Beads_Integration.md#reproduce-acceptance).
Runtime users install only the optional tools they need. The Odoo-only
environment also runs all 33 representative CLI fixture cases and evidence
retrieval. Stdio/process tests require a host runtime that
supports child process communication; they do not complete in this agent's
restricted execution sandbox.

See the [architecture](docs/Composable_Developer_Tookkit_Architecture.md) and
[implementation plan](docs/Implementation_Plan.md) for the fresh-build decisions
and later increments. Live Odoo, tracker imports, Beads mutation/server modes,
and orchestration remain future work with separate integration prerequisites.
